## Blocking findings

### F1 [behavior] Pool-resolver and liveness fixtures bypass Phase 6 provisioning, which the charter row requires
The charter verification plan says the pool-resolver row runs "on a Dandan-config state built through Phase 6's provisioning". Plan section 8 intro and V8/V9 push one `PlayerDeckPool` by hand and state it "is the shape Phase 6's provisioning produces". The equivalence is the premise every U2 row and V9 stand on (one pool, at the canonical seat only, none for P1); Phase 6's V1 asserts only `deck_pools.len() == 1` and `player == P0`, so a hand-built pool cannot catch a provisioning shape the resolver does not resolve.
Required revision: V8 (resolver row) and V9 build the state by calling the Phase 6 provisioning entry that needs no card database (`engine::game::deck_loading::load_deck_into_state`, `pub`, plus the Dandan seat gating of Phase 6 section 3.5) on a `GameState::new(FormatConfig::dandan(), 2, seed)` with a `DeckPayload` carrying a list for BOTH seats; the reach-guard asserts `deck_pools.len() == 1`, `deck_pools[0].player == P0`, `players[1].library` empty, `deck_pool_of(P1)` is that pool. V5/V6/V7 may keep the hand-pushed pool (they are function-level and need exact multisets), but the section 8 sentence must be replaced as in F6. If `load_deck_into_state` cannot be used without a database at PHASE_BASE, say so in the plan and keep the hand-built pool for that row only, with the reason.
