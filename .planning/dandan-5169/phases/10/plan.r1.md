Why these cards, not the brief's examples: Accumulated Knowledge goes through the id-deduped `ObjectCount` path and cannot fail (brief, Count dedup); the brief's list cards use none of the three arms.

**The "your graveyard" reading adopted.** For a card in a shared graveyard or library, "your graveyard" / "your library" is the shared zone for every seat: any seat's "you", "an opponent" or other player reference is satisfied by the shared pile, and a count over "your graveyard" for any seat is the count of the one pile. Source: the announcement the brief quotes verbatim, "Players have a shared library and graveyard. Anything referring to "your" graveyard or library is referencing the shared zone." (brief, Authoritative rules), the brief's Filter owner-axis collapse section ("treat the axis as satisfied for every seat"; "Opponent-scoped text collapses the same way (the July convention)") and the Count dedup section. CR background, each grepped in `docs/MagicCompRules.txt`: CR 400.1 ("Each player has their own library, hand, and graveyard") is the rule the format modifies; CR 400.3 (an object goes to its owner's corresponding zone) and CR 404.1 ("A player's graveyard is their discard pile") are why the stored container is keyed by owner; CR 108.4a + CR 109.5 ("you" for a card with no controller means its owner) are why the engine reads "your graveyard" as an ownership claim. No CR text addresses a shared graveyard; the reading rests on the announcement, and this plan says so rather than citing a CR for it. The "Opponent" half rests only on the brief's July-convention sentence and no Dandan-list card exercises it (the brief says so); it is implemented and tested on Disposal Mummy and Nighthawk Scavenger and flagged in the claims ledger as the brief's call, not a rules derivation.

Charter claim 1 re-measured, and it is false in its consequence: `grep -n matches_target_filter_in_owner_zone crates/engine/src/game/targeting.rs` has no hit, but `targeting.rs::add_zone_targets` and the target re-validation near `matches_target_filter_for_zone` call `filter::matches_target_filter_for_zone`, whose `is_owner_scoped_zone` arm (Hand, Library, Graveyard) delegates to `matches_target_filter_in_owner_zone` (read at `filter.rs`, `matches_target_filter_for_zone`). So target legality for a graveyard object DOES run through the owner-zone function. That function does not skip the controller axis: it overwrites `controller` with `owner` and then runs `filter_inner_for_object`, whose typed-filter controller arm compares `owner` with the source's controller. Consequence for the design: one collapse placed at the typed-filter controller arm (keyed on `obj.zone`) covers both `matches_target_filter` and `matches_target_filter_in_owner_zone`, and `matches_target_filter_in_owner_zone` needs no edit of its own. The charter's "controller collapse is independently required for Mystic Sanctuary" stands (Mystic Sanctuary has only the controller axis), but its stated reason is replaced by this one.

## 3. Design

### 3.1 Unit A: the shared-zone axis collapse (game/filter.rs)

One authority, `zone_axis_admits`, answers: does the axis comparison hold against `holder` or against any seat that reads the same container of `zone`?

```text
fn zone_axis_admits(state, zone: Option<Zone>, holder: PlayerId, admits: impl FnMut(PlayerId) -> bool) -> bool
```
- `None` (a record with no origin zone, e.g. token creation) or a zone whose container is per seat: only `holder` is tried, so every non-shared case runs the existing comparison exactly once on exactly the same value (identity).
- `Some(zone)` with a shared container: `holder` first, then every other seat `s` in `state.players` with `state.zone_storage_seat(zone, s) == state.zone_storage_seat(zone, holder)`. The seat set is derived from Phase 6's single storage authority; no second Zone-to-`ZoneScope` table is written here (the alternative, a new `is_zone_shared(zone)`, would duplicate the mapping `zone_storage_seat` already owns). `holder` is always tried even when it is not in `players`.
- `any` over those seats gives exactly the brief's "satisfied for every seat": `You` is satisfied by the seat equal to the source's controller; `Opponent` by any other living seat; `ScopedPlayer`, `TargetPlayer`, `ChosenPlayer`, `SpecificPlayer` and the rest by the seat the reference names, provided it is a seat that reads the container.

Edits, all in `filter.rs`:
1. Typed-filter controller arm of `filter_inner_for_object` (the arm that calls `effective_controller`): the existing `match ctrl { .. }` body moves unchanged into a closure `|obj_ctrl: PlayerId| -> bool { match ctrl { ..existing arms, each `return false` kept.. } true }`, and the arm becomes `if !zone_axis_admits(state, Some(obj.zone), effective_controller(..), admits) { return false; }`. The arms are not rewritten (they hold the trigger-aware defending-player and chosen-player resolutions; `controller_ref_player` is NOT reused because its `DefendingPlayer` and `TargetPlayer` resolutions differ from the inline arms). The only textual change inside the arms is rustfmt re-indentation.
2. `FilterProp::Owned` has two near-identical 16-arm bodies, one in `matches_filter_prop` (compares with `obj.owner`) and one in `zone_change_record_matches_property` (compares with `record.owner`); both take `source: &SourceContext<'_>`. They collapse into one `owned_axis_admits(state, source, controller: &ControllerRef, owner: PlayerId) -> bool` (the bodies with `owner` in place of `obj.owner`/`record.owner`, annotations kept) and each arm becomes one call: live `zone_axis_admits(state, Some(obj.zone), obj.owner, |owner| owned_axis_admits(state, source, controller, owner))`, record `zone_axis_admits(state, record.from_zone, record.owner, ..)`. The record arm keys on `record.from_zone` because the record's `InZone` arm already means `record.from_zone == zone` (read), so "owned and in a zone" is evaluated against the same zone on both sides. Net effect: two copies become one authority, which is the reviewer-visible simplification that pays for the new helper.
3. `matches_target_filter_in_owner_zone`: no edit (see 0). Its owner override and its `obj.controller == obj.owner` fast path both feed edit 1.
4. Not collapsed, with reasons: (a) the record typed-filter controller axis (`zone_change_filter_inner`'s `record.controller` match) because `record.controller` is the battlefield or stack controller at departure and a creature "you control" dying into the shared graveyard must still mean its controller (collapsing on `to_zone` would make "creature you control dies" fire for the opponent's creatures); (b) `FilterProp::Owned` on objects whose zone is per seat (battlefield, hand, stack, exile), unchanged; (c) the stack-entry controller check and the `FaceControllerScope` arms (no shared zone reaches them).
5. Known boundary, not fixed here (verdict, claims ledger): destination-phrased triggers such as Angelic Renewal's "Whenever a creature is put into your graveyard from the battlefield" are lowered to `valid_card: Typed{Creature, controller You}` with `origin Battlefield`, i.e. to the battlefield-controller axis, so (4a) leaves them firing only for the observer's own creatures. Re-expressing them needs a parser change (out of charter); none of the 23 Dandan-list names has such a trigger (measured, see ledger).

CR annotations written: CR 400.1 (modified by the format's shared-zone axis, per the announcement), CR 400.3, CR 404.1, CR 108.4a + CR 109.5. Each grepped; no other number.

### 3.2 Unit B: count dedup with the three arms' reads (game/quantity.rs)

Dedup key and keyed population, modelled on `topology::shared_resource_dedup_key` + `players::aggregate_over_teams` (both exist: `grep -n "fn shared_resource_dedup_key\|fn aggregate_over_teams"` over `topology.rs` and `players.rs` returns one hit each; both stay read-only, and the key type is `PlayerId`, so no signature in them changes):

```text
fn zone_dedup_key(state, zone: Option<Zone>, player: PlayerId) -> PlayerId   // zone.map_or(player, |z| state.zone_storage_seat(z, player))
fn distinct_zone_holders<'a>(state, zone: Option<Zone>, players: impl IntoIterator<Item = &'a Player>) -> impl Iterator<Item = &'a Player>   // first-seen per key
```
`aggregate_over_teams` needs its own fold because its scalar is team-level; here only the population changes while the scalar stays a per-player extractor, so the keyed fold is `aggregate_over_players(distinct_zone_holders(..), aggregate, extract)` with no new fold function. `None` is the identity key (a scalar the player holds itself); `Some(zone)` is a container read.

Edits, all in `quantity.rs` (each arm's accessor read and its key are one edit):
1. `scoped_zone_holders(state, zone: &ZoneRef, scope, ctx, controller)`: `distinct_zone_holders(state, Some(zone.zone()), scoped_players(..))`. `ZoneRef::zone()` is the existing single mapping (read at `types/ability.rs`). Hand and Exile resolve to identity (Hand is per seat: `zone_storage_seat(Zone::Hand, s) == s` by Phase 6 3.1; Exile never reaches it).
2. `visit_characteristic_leaf`, `CardTypeSetSource::Zone` Graveyard/Library/Hand arm: `for player in scoped_zone_holders(..)` and the container read becomes `state.graveyard_of(player.id)` / `state.library_of(player.id)` / `&player.hand` (a small private `zone_container(state, zone, player)` shared with the next arm, so the three-way match exists once).
3. `QuantityRef::ZoneCardCount`, per-player zones arm: the same `scoped_zone_holders` and `zone_container`. The Exile arm is untouched (it already predicates per object, so it counts the object once).
4. `QuantityRef::GraveyardSize`: today `resolve_per_player_scalar(.., |p| p.graveyard.len())`. `resolve_per_player_scalar` keeps its signature as a one-line wrapper over `resolve_per_zone_scalar(state, zone: Option<Zone>, scope, ..)`, whose `Opponent` and `AllPlayers` arms fold `aggregate_over_players(distinct_zone_holders(state, zone, population), ..)`; the single-player scopes are unchanged. The arm calls the `Some(Zone::Graveyard)` form with extractor `|p| usize_to_i32_saturating(state.graveyard_of(p.id).len())`. The ~14 other callers of `resolve_per_player_scalar` are untouched (identity key).
5. `resolve_player_count`, `PlayerFilter::PlayerAttribute` arm (this is Phase 8's "all-seats count is Phase 10's dedup axis"; the parser lowers "for each graveyard with seven or more cards in it" to a count of players whose graveyard has seven, which on a shared graveyard visits one pile once per seat): a `BTreeSet<PlayerId>` declared before the `.filter(..)` chain, and the arm ends `&& counted.insert(zone_dedup_key(state, player_attribute_container_zone(attr), p.id))`, so the key is inserted only for a candidate that already passed `relation` and the comparison (relation `Opponent` over a two-seat shared pile still counts the pile once). `player_attribute_container_zone(attr: &QuantityRef) -> Option<Zone>` is `GraveyardSize{..} => Some(Zone::Graveyard), _ => None`; the wildcard mirrors `candidate_player_scalar`'s closed scalar subset (every other attribute is a per-player scalar with the identity key).
6. Not edited, with reason: `effects/mod.rs::matches_player_scope` (the other `PlayerAttribute` copy) selects the players who each ACT ("each player whose graveyard has seven or more cards, that player mills"); both seats satisfy the text and both act, so visiting seats there is correct, not a double count. `object_count_matching_candidate_ids` and `ObjectCount` stay raw and id-deduped (brief). The per-player journals (`SpellsCastThisTurn`, `PlayerCounter`) are not zone containers.

Observability of the dedup per arm (stated so no row claims more than it can show): the `CardTypeSetSource` consumers (`DistinctCardTypes`, `DistinctSubtypes`, `DistinctColorsAmong` into a `HashSet`; `Aggregate` through `seen.insert(member)`) already dedup by member or by set, so the key does not change any result for that arm; the shared helper keeps the three arms on one population authority, and the arm's discriminating row is the accessor conversion. `ZoneCardCount` with scope All (a sum) and the `PlayerCount` over a graveyard scalar are the two places where the key changes a result at a real card; `GraveyardSize` under `Max`/`Min` aggregates is key-insensitive (equal values) and under `Sum` (no supported card) is covered only by the building-block unit row.

CR annotations: CR 400.1 (shared-zone modification), CR 404.1, CR 109.5; each grepped.

## 4. Building blocks, logic placement, idioms

- Logic placement: all in `engine`; no transport or frontend change.
- Rust: typed `Option<Zone>` (no bool), exhaustive `match` in the helpers, one documented wildcard in `player_attribute_container_zone`.
- Nom compliance: no file under `crates/engine/src/parser/` changes.
- Extension vs creation: extends the owner-keyed container read with the shared-zone key the 2HG precedent already uses for teams; creates no second store and no new enum.
- Analogous trace: 2HG shared life: `topology::shared_resource_dedup_key` → `players::aggregate_over_teams` → `quantity::resolve_per_team_life` (`quantity.rs`) → `QuantityRef::LifeTotal` arm; filter side: `filter::matches_target_filter_for_zone` → `matches_target_filter_in_owner_zone` → `filter_inner_for_object` → `targeting::add_zone_targets`; count side: `resolve_ref` `GraveyardSize` → `resolve_per_player_scalar` → `aggregate_over_players`, and `resolve_player_count` → `candidate_player_scalar_with_state`.

## 5. Identity / provenance contract

Source phrase: "Anything referring to 'your' graveyard or library is referencing the shared zone." Authority: the seat set reading one container, derived each evaluation from `zone_storage_seat` (no stored copy); the named player (the source's controller, a target player, a chosen player, a scoped player) is bound by the existing arm exactly as today. Binding time: live evaluation for the typed-controller and live-`Owned` arms (keyed on `obj.zone` at evaluation); event-time for the record `Owned` arm (keyed on `record.from_zone`, a snapshot field); count arms evaluate the key at resolution. Invalidation: none (the seat set never shrinks, Phase 6 3.1). Multi-authority hostile fixtures: (a) owner ≠ controller: a pile card with `controller` set to the other seat (the state `matches_target_filter_in_owner_zone` defends against) still admits both seats; (b) owner ≠ storage seat: a P1-owned card stored in the canonical seat's container admits both P0's and P1's `You`; (c) the same card evaluated on the battlefield (controller P0) admits only P0 (per-seat zone, no collapse); (d) source seat canonical versus non-canonical for every row.
