**The engine's effect identity, MEASURED by reading, is `ContinuousEffectGroupKey` (via `continuous_effect_group_key(state, entry) -> Option<_>`)**, not the timestamp and not the entry:
- Its own doc: "Identity of one continuous effect whose modifications may apply in several layers. The identity deliberately excludes `mod_index`: every modification produced by the same effect shares the CR 613.6 affected-object set." Variants: `Static { source: ObjectIncarnationRef, definition_index }`, `Transient { continuous_effect_id }`, `GrantedStatic { grant_origin, recipient }`. It is already the key of `started_effect_sets` (so `apply_continuous_effect` and the ordering would agree on "which effect is this", the property the copy-layer fixed-point loop's doc stresses).
- The gather sites assign one identity to every modification of one effect: the printed-static site loops `def.modifications.iter().enumerate()` pushing `def_index: Some(def_index)`; the transient site loops `tce.modifications.iter().enumerate()` pushing `transient_id: Some(tce.id)` on every entry (read, this is exactly the room test's `CopyValues` + `SetName`); `expand_granted_static_effects` pushes `def_index: None, transient_id: None` with `trigger_producer_origin` set (the `GrantedStatic` arm); `stickers.rs` builds entries with no def/transient id (key `None`).
- Timestamp is NOT an identity: all statics on one object share its timestamp (613.7a), so equal timestamps do not mean one effect. `source_id` is NOT one either: one source carries several statics and several transient effects.
- Consistency with the existing same-effect guard in `depends_on` (it suppresses edges when `(source_id, def_index, transient_id)` are equal): two entries with equal group keys always have equal triples (Static key fixes source and def_index, with `transient_id` None on printed entries; Transient key fixes the tce id and therefore its source; GrantedStatic key fixes the recipient, which is `source_id` there, and both indices None). So **no dependency edge ever exists between two entries of one effect**, which the §5 termination argument needs. The converse does not hold only for `GrantedStatic` effects from different origins on one recipient (the guard's triple collides there, the key distinguishes them); the guard is left as is (changing it would alter acyclic behaviour) and the finer key is used for nodes; the two statics simply have no edge between them either way.
- `continuous_effect_group_key` returns `None` when the source object is gone (`Static`) or provenance is missing; such an entry forms its own one-entry effect.

## 5. The rule, derived from CR 613.8, over effects

1. **Entries.** Sort the bucket's entries by the existing key; `sorted[i]` is entry rank `i`.
2. **Effects.** `members = effect_nodes(&sorted, state)`: node `n` is one effect; `members[n]` its entries in intra-effect (written) order; node rank = rank of its first entry. A modification that is not an effect of its own does not get a node (CR 613.8a speaks of effects).
3. **Edges.** Edge `P -> Q` (Q depends on P) iff `P != Q` and some entry `q` of Q has `depends_on(q, p, state)` for some entry `p` of P. Edges are deduplicated per ordered node pair; `dependents[P]` lists the Q's; `in_degree[Q]` counts distinct P's. Computed once (CR 613.8c stays satisfied exactly as today because `depends_on` is state-blind).
4. **Order.** `dependency_application_order(dependents, in_degree)` over nodes: repeatedly apply the lowest-ranked unapplied node with in-degree 0 (613.8b "waits until just after all of those effects"; timestamp tiebreak among simultaneous dependents). On a stall, every remaining source strongly connected component has at least two nodes (a singleton source node would have in-degree 0; self-pairs are skipped and edges are deduplicated, so in-degree is exactly the count of unapplied distinct dependencies). Pick the source component whose lowest-ranked node ranks lowest, delete the edges internal to it (each lowers its target's in-degree once), resume. After deletion every node of the component has in-degree 0 (no edge into it from outside, by the source property), so they apply by rank (613.8b "applied in timestamp order"). Nodes depending on loop members keep their in-degree from the loop and wait for the members they depend on. Stalls recur for further loops.
5. **Expansion.** The result expands each applied node into its entries in `members[n]` order (consecutively). Entries of one effect therefore apply contiguously in written order (613.7a), whether or not the effect is in a loop.

Termination: every cycle of the loop applies at least one node (after a deletion the chosen component's nodes have in-degree 0). Whole-loop bucket: all edges internal, all deleted, pure rank order (identical to today's fallback outcome). A bucket where each effect owns one entry is identical to the round-0 entry-level rule (nodes = entries), so H1-H6 and R1-R4 are unchanged.

Reading left open, stated so the executor does not guess: a dependent that depends on only some loop effects becomes eligible as soon as those effects have been applied and then applies at its own rank (it may apply between two loop effects: literal 613.8b/613.8c). Phase 5's three-Hack case yields A, B, C under both readings. A loop effect that also depends on an effect outside the loop waits for that effect.

### Behaviour change on acyclic buckets, stated and bounded
Effect-level nodes can change an ACYCLIC order only where one effect's entries are treated differently by today's entry-level pass. Entries of one effect share `affected_filter`, and `depends_on(a, b)` reads `a` only through `a.affected_filter` (and the unconditional `CopyValues` arm), so all entries of an effect have the same incoming dependencies: they become eligible together. The only difference is an older dependent entry `D` that depends on a strict subset of the effect's entries (it can currently apply between two entries of one effect, splitting it, which contradicts 613.7a/613.8b). Under effect nodes `D` waits for the whole effect. This is rules-correct, rare (needs a multi-entry effect in the same bucket plus a dependent that reads only some of its entries), and is closed by the full suites in §6 step 4: any changed outcome fails a test and is a stop-and-return.
