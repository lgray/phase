## Blocking findings

### F1 [behavior] V8 revert claim is false, so the row does not discriminate
Plan V8: "Revert `zone_container_len` to the raw owner read: replay returns `DestinationPositionMismatch`".
Measured (`game/zones.rs` 901-968 and 1112-1136): `destination_position` is captured live by `destination_position_after_removal` -> `zone_container_len` (line 955) and recomputed at replay by the same function (line 1112). A revert changes both sides alike (P1 raw len = 0 on capture and on replay), so they agree and no mismatch is raised. Replay also still installs through the routed `add_to_zone`, so `library_of(P0)` matches too. As written V8 passes with the revert.
Fix (text): replace the assertion with a direct pin on the recorded command: `command.destination_position == pile_len_before_move` (the field is public on `ResolvedZoneChangeCommand`, `resolved_commands.rs:929`), plus the replayed pile equals the live pile. Revert then records 0 against 66 (or the test pile length) and fails. Replace the old string "Revert `zone_container_len` to the raw owner read: replay returns `DestinationPositionMismatch`" with "Revert `zone_container_len` to the raw owner read: the recorded `command.destination_position` is 0 instead of the pile length". The same check should also pin the graveyard arm (a P1-owned card to the graveyard: `destination_position == graveyard_of(P0).len()` before). Keep the `DestinationPositionMismatch` mention out.

### F3 [text] The engine-wasm boot-guard call site is pinned by no test
Plan V1/V13 revert the engine predicate `seats_with_empty_library`, never the wasm call. Measured: the guard lives in `initialize_game_impl` (`engine-wasm/src/lib.rs:1729`, guard at 1903-1908), which takes and returns `JsValue` (`to_js`, `serde_wasm_bindgen`) and is not callable from a native test; the native tests at `lib.rs:6555` drive other seams. (i) is preferred. Add to 3.7: "the call site is pinned by <mechanism>".

### F4 [text] V9 (and V5) fixtures: `add_real_card(.., Zone::Library)` does not place "on top"
Plan V9: "`add_real_card(P1, "Island", Zone::Library)` on top". Measured (`game/scenario_db.rs` 72-130): `add_real_card` creates the object, `remove_from_zone`, then `add_to_zone(.., zone, player)`, which appends at the bottom. Top placement exists only in `add_spell_to_library_top` / `add_card_to_library_top`, both of which (scenario.rs:283, 1001) re-seat with raw `players[player].library.retain/insert(0, id)` — for a P1-owned card in a Dandan state that inserts the id into P1's own empty container while `create_object` has already put it in the pile: the same two-container corruption the phase exists to prevent. scenario.rs is outside the scope paths and must not be used for P1-owned library-top cards.
Fix (text): state that V5/V9 build the pile with `add_real_card` (bottom, routed) and then reposition with the new accessor in the test (`let l = state.library_of_mut(P0); l.retain(..); l.insert(0, id)`), asserting the intended top three afterwards as the positive reach-guard. Also add to the plan that the fixture helpers `add_card_to_library_top` / `add_spell_to_library_top` are not used with a non-canonical owner.

## Adjudications requested

### (a) `scripts/zone_authority_census.py`
Evidence: it is a committed CI gate. `.github/workflows/ci.yml:109` runs `./scripts/check-engine-authorities.sh "$BASE"`, which runs `zone_authority_census_tests.py` (section B0, line 144) and `zone_authority_census.py --check` (section B, line 149); four sibling scripts import from it (`draw_replacement_census.py`, `cr733_mutation_census.py`, `post_replacement_continuation_census.py`, `lib/detect-cross-product-alts.py`). The charter names it only as a measuring command (Phase 6 claim 2: "regenerable command ... re-run at phase start"), never as a path to edit.
Classification: it is an ordinary lockstep update of an existing gate that the scope rule should have named (a new write authority, `library_of_mut`, is invisible to the gate's `CONTAINERS` regex, which keys on `.library.push_back(`), not "verification machinery that needs an expansion case". It is, however, not needed to close the phase: measured, `--check` passes at HEAD and the plan's edits produce no new census hit on the unmodified gate (mulligan's `&mut ..library` into `shuffle_vector` is BORROW-exempt today and has no row; `library.rs`/`conjure.rs` whole-container assignments have no row today either). Phase 6's claims (write-side routing, replay determinism, pool resolver, guard) all close without it.
Recommendation: a charter decision question for the orchestrator (amend Phase 6's scope rule or assign the gate extension to a later phase); the phase plan drops the path now (F2). If amended, the extension needs its own test case in `scripts/zone_authority_census_tests.py` (HardGateTests pattern: one synthetic `x.library_of_mut(p).push_back(i)` hit unannotated fails, annotated passes, `fn library_of_mut(` definition not matched), which is a 13th path; T1 still fails so no split is forced.
