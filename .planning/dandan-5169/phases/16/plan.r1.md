## 3. Design

### 3.1 Engine: the descriptor (`crates/engine/src/game/derived_views.rs`)

```rust
/// CR 400.1 as modified by the format's shared-zone axis: which seat's
/// container stores each shared pile. A zone absent here is per-player.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub struct SharedPilesView {
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub library: Option<PlayerId>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub graveyard: Option<PlayerId>,
}
```

- `DerivedViews` gains `#[serde(default, skip_serializing_if = "Option::is_none")] pub shared_piles: Option<SharedPilesView>`, placed beside `debug_library_cards`. A non-shared format serializes byte-identically to today (the key is absent).
- `fn shared_piles(state: &GameState) -> Option<SharedPilesView>`: `let zones = state.format_config.format.shared_zones();` an exhaustive `match` on each zone's `ZoneScope` (no wildcard): `Shared => Some(state.canonical_seat())`, `PerPlayer => None`; the result is `None` when both are `None`. Called once in `derive_views` (`shared_piles: shared_piles(state)` in the struct literal). `derive_filtered_views` calls `derive_views(filtered_state, ..)`, and the format and seat set survive filtering, so it needs no override line (E3 asserts this rather than assuming it).
- Why a descriptor and not a per-seat map: the client needs one answer per zone ("which seat holds it"), and the map would add a field per seat to every snapshot for a fact with at most two values. The `?? seat` fallback in the client helper (3.3) is a lookup of this engine value, not a computation.
- Single authority: the holder is `canonical_seat()` (Phase 6) and the scope is `shared_zones()` (Phase 2), the same two inputs `zone_storage_seat` reads. E1 pins that the descriptor and the storage agree (a card moved through `library_of_mut(P1)` lands in `players[holder].library`), so the two cannot drift silently.
- `debug_library_cards` (`DebugLibraryViewer`): Phase 8's plan converts it to `library_of` (M3, row V10a: `grep -n "debug_library_cards" phases/8/plan.md`). This phase does not re-edit it. Claim to establish at phase start: `grep -n "library_of\|\.library" crates/engine/src/game/derived_views.rs` shows `debug_library_cards` reads `library_of(viewer)`. If Phase 8 did not land it, the executor converts that one read here (the file is in scope) and E5 is red at base; if it did, E5 is a green guard.

### 3.3 Client: one pile-seat authority and every site routed through it

`client/src/adapter/types.ts`: `export interface SharedPilesView { library?: PlayerId; graveyard?: PlayerId }` with a doc ("Mirrors `engine::game::derived_views::SharedPilesView`; a missing key means the zone is per-player") and `shared_piles?: SharedPilesView` on `DerivedViews`, beside `debug_library_cards`.

`client/src/viewmodel/gameStateView.ts` (the existing home of `getPlayerZoneIds`) gains three pure functions, the only readers of the new field:
- `getSharedPileHolder(gameState, zone: "graveyard" | "library"): PlayerId | null`: `gameState?.derived?.shared_piles?.[zone] ?? null`.
- `resolvePileSeat(gameState, zone, seat): PlayerId`: `getSharedPileHolder(..) ?? seat`. It selects between two engine-provided values; it derives nothing.
- `getZoneViewerPile(gameState, obj): { zone: "graveyard" | "exile"; playerId: PlayerId } | null`: null outside Graveyard and Exile; `playerId` is `resolvePileSeat(gameState, "graveyard", obj.owner)` for a graveyard object and `obj.owner` for exile (exile stays per-seat).

4. `hooks/useCastableZoneObjects.ts`: the graveyard branch reads `players[resolvePileSeat(..)]`'s graveyard, so both seats' hand fans show the engine's castable wings from the one graveyard. Exile branch unchanged.

The `ownerId` in the mill branch is `obj.owner`, which under Phase 11's rebind is not the holder; the HUD fallbacks (`getPlayerHudPosition`) stay seat-keyed (they are HUD anchors, not piles).
6. `pages/GamePage.tsx`: (a) the `opponentPiles` widget renders `ExilePile` always but `LibraryPile` and `GraveyardPile` only when `getSharedPileHolder(gameState, "library")` / `"graveyard"` is null, so the shared piles render once, in `playerPiles` (whose three components already resolve through 2 and 3 and need no edit); (b) the auto-open loop (`groups.add(`${zone}:${obj.owner}`)`) and `getCastableZoneViewerTarget` both use `getZoneViewerPile`, so a prompt over cards of the shared graveyard owned by both seats is one group, not two. `getCastableZoneViewerTarget` gains a `gameState` parameter (compiler-forced: 5 call sites in `gameStateView.test.ts`).

It becomes `resolvePileSeat(gameState, "graveyard", playerId) === resolvePileSeat(gameState, "graveyard", viewerId)`.

## 5. Pattern coverage, building blocks, placement, idioms

**Building Blocks.** Engine: `GameFormat::shared_zones`, `ZoneScope`, `GameState::canonical_seat` (Phase 6), `derive_views`/`derive_filtered_views`/`ClientGameStateRef`. Client: `getPlayerZoneIds` and its module, `useGameStore` selectors with primitive results, the `PileAnchors.test.tsx` / `LibraryPile.test.tsx` patterns, `buildGameState({ derived })`, the `VisualPackAnimations.test.tsx` `seedOverlay` harness, the `GamePage.optionalEffectChoice.test.tsx` mock harness. No new helper duplicates an existing one: `resolvePileSeat` is the single authority, `getZoneViewerPile` replaces two duplicated owner-keyed group loops.

**Logic Placement.** Rule/identity logic (which seat holds a pile) is in the engine, one function. The client has no conditional on a format name, a seat count, or a canonical-seat rule; it reads an engine value and chooses between it and the passed seat. No transport edit (the wire is a serialized field of an existing view).

**Rust Idioms.** Typed `Option<PlayerId>` per zone (not a bool, not a sentinel seat); exhaustive `match` on `ZoneScope`; `Copy` struct; `skip_serializing_if` so non-shared output is unchanged. **Nom Compliance:** no file under `parser/` changes. **Extension vs Creation:** extends the `derived_views` presentation layer (the documented home for "the frontend would otherwise have to compute", per the struct's doc comment) and the `getPlayerZoneIds` seam.

**Analogous Trace.** `visible_exile_object_ids` / `debug_library_cards` end to end: `game/derived_views.rs` (field, derive fn, `derive_views`, `derive_filtered_views`) -> `ClientGameStateRef::wrap` / `wrap_filtered` -> `engine-wasm/src/lib.rs` `to_js` and `server-core`'s `derive_transport_views` (`crates/phase-server/src/main.rs`) -> `client/src/adapter/types.ts` `DerivedViews` -> `viewmodel/gameStateView.ts` / component selectors.
