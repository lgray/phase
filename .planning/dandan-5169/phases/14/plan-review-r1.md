## Findings

### F1 (behavior, blocking): the dealer intercepts skip the per-effect action recording

The sequential layer-1 fan-out records `PlayerPerformedAction` through the nested `resolve_ability_chain` of each seat: the fold into `player_actions_this_way` and `record_player_action_this_turn` sits in the effect step of `resolve_chain_body` (`effects/mod.rs:~16667-16676`, after `let events_before = events.len()` at `:16132`), which the layer-1 driver and the layer-2 branch both `return Ok(())` before reaching. The plan's `Completed` branches (3.4) push `EffectResolved` and run the tail but never fold the `PlayerPerformedAction` events the dealer emits in `draw.rs`. Consequence: under a shared library a completed each-player-draws instruction leaves `player_actions_this_turn` without the `(seat, Draw)` entries (read by `QuantityRef::PlayerActionsThisTurn { action: Draw }`, `quantity.rs:6214-6232`) and `player_actions_this_way` without the drawers (read by `PlayerFilter::PerformedActionThisWay`, e.g. Kwain's shape). The doc of `record_player_action_this_turn` (`:18392`) states `resolve_chain_body` records every such event in its window.
Required revision: (1) extract the 8-line fold into one helper used by the effect step and by both dealer `Completed` branches (no fourth copy); (2) V1 and V3 gain a parity row: after the dealer, `player_actions_this_turn` holds exactly one `(P0, Draw)` and one `(P1, Draw)` and `player_actions_this_way` holds both, with the paired sibling (V2, sequential) asserting the same values; (3) state in 3.4 that the parked-then-resumed completion records nothing, in parity with the existing sequential parked path (the choice handler records only Scry, `engine_replacement.rs:~718`), as a stated pre-existing limit.

### F2 (behavior, blocking): the unscoped tail is placed with `append_to_pending_continuation` on the `Parked` branch

3.4 says `Parked` -> `append_to_pending_continuation(state, after_scope)` and "the unscoped tail drains at the existing boundary after the dealer's frame completes". That holds only when the dealer's own MultiDraw is the stack top (the `active_frame_requires_ability_continuation_parent` arm inserts below it). When the park comes from a nested instruction inside Settling (P3 case (ii): Alms Collector on P0 plus a draw prompt on the nested draw, e.g. Obstinate Familiar on P0), `append_to_pending_continuation` (`effects/mod.rs:2554-2615`) either appends to the tail of the nested chain's already-parked sub continuation (`active_ability_continuation()` arm) or takes the `has_active_post_replacement_draw_pair` arm, which inserts "outside the pair", i.e. directly above the dealer's MultiDraw. In both shapes the tail drains when the nested pair retires, before the dealer finishes Settling and before any card is dealt, and the dealer frame is then resumed only at a later boundary. The sequential path never exposed this because the outer frame owes nothing after its consult.
Minimal correct design: the dealer's `Parked` branches (layer 1 and layer 2) insert the tail with `state.insert_ability_continuation_parent_at_child_boundary(PendingContinuation::new(tail, state), child_stack_start)` where `child_stack_start` is the `capture_child_boundary()` value `resolve_chain_body` already takes at entry (`effects/mod.rs:14749`; existing use at `:17941` for the same reason: "insert it outside the whole child stack"). That places the tail below the dealer frame and below every nested pair in every shape, and is equivalent to the parent-of-active arm in the non-nested case.
Required revision: change 3.4 accordingly, and add one hostile row to the matrix: a scoped Draw head with a non-optional unscoped tail (built as a `ResolvedAbility` through `resolve_ability_chain`, the planner's own fallback for P2) on a Dandan state with Alms Collector and Obstinate Familiar both under P0; assert every dealt card is delivered before the tail runs, with the paired positive that the tail does run after the final prompt is answered. P3's stop-and-return clause stays for the dynamic case-(i) probe.
