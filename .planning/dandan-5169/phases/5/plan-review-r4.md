## Judgement on (2): loop-only (SCC) fallback in `order_with_dependencies`
- Rules: the existing whole-bucket fallback IS wrong under CR 613.8b. 613.8b: a dependent effect waits until just after all effects it depends on; only "several dependent effects [that] form a dependency loop" lose this and apply in timestamp order. The fallback reverts every effect in the layer bucket, including non-loop dependents, so it contradicts the rule; the code's own comment admits this as a tracked deviation. That is a defect in a reference the phase depends on, and its "unreachable today" justification is false (R4-3): loops are reachable whenever two typed-filter type-changers coexist. The plan's SCC algorithm is exactly what 613.8b says for the loop and for its dependents: Kahn stall implies every source component is a nontrivial loop (a trivial source would have in-degree 0), internal edges removed once, loop members then apply in timestamp order, downstream dependents wait for all of them. Hand-run of the plan's three-Hack case (B ts1, A ts2, C ts3 => A, B, C, Forestwalk) is correct. One reading the CR does not settle: a loop member that also depends on an effect OUTSIDE the loop; the plan applies the upstream effect first (Kahn), which is a defensible reading of "just after all effects it depends on", not a defect.
- Blast radius (measured by grep/read, test outcomes not runnable): `order_with_dependencies` is reached from the full pass (3217) and incremental pass (6192) for every layer with `has_dependency_ordering()` (Copy, Control, Text, Type, Ability, CharDef, SetPT, ModifyPT) and via `order_active_continuous_effects` (Copy fixed point 5924/6127/9840, SetPT test 13244, off-zone Ability collector). Outcome can change only for buckets with a loop AND an effect outside it. Named: (a) `mutually_copying_permanents_reach_a_layer_one_fixed_point` (26245): reordered, assertions not sensitive (R4-2); (b) `double_urborg_*` (21922) and the other 2-effect Urborg tests: whole-bucket loop, identical; (c) `same_static_modifications_apply_in_written_order` (24235): intra-static edge suppressed, no loop, unaffected; (d) real boards: two Clones/copies plus a copy-layer static from a copied object, or Type-layer loop (Blood Moon/Urborg/Frogify-style typed type-changers) plus a third effect with a typed recipient that is not itself in `b_changes_types` (e.g. a `RemoveAllSubtypes` clause from another source). No test I found asserts such a shape; a full layers + integration run is the only proof, and the plan already makes it a stop-and-return gate.
- Belongs in this phase? Not needed to close R3-1 (guard (1) plus grouping (2) suffice). It is needed only for one corner (three+ Hacks on one object where a same-`from` pair coexists with a chain). It is a rules-correct fix to shared machinery and is cheap, so keeping it is acceptable, but it widens the phase into every layer and needs the layers.rs charter revision the plan already requests. If the orchestrator prefers a smaller blast radius, dropping (3) and the "chain-plus-loop on ONE object" P4 row, recording that corner as the existing tracked 613.8b deviation, is also sound. I recommend keep (it is correct, bounded, gated), with R4-1/R4-2 text fixes and an explicit charter note that it changes shared layer behavior for all layers.
