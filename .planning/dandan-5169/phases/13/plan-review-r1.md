## Findings

### F1 [behavior, blocking] The close's `CardsRevealed` is published by the apply-boundary hook against the post-redeal objects, which the plan says does not happen

Plan 3.4 item 2: "`reveal_hand` emits one `GameEvent::CardsRevealed { player, card_ids, card_names }` ... no `revealed_cards` set is written because the hand leaves the zone in this same close."

Measured against HEAD:
- `crates/engine/src/game/engine.rs:2023` and `:9402` call `remember_public_reveals(state, &result.events, journal_start)` once at the END of every `apply`, after the whole action (here: return, shuffle and redeal) has run.
- `remember_public_reveals` (`engine.rs:8202-8252`) loops over every `GameEvent::CardsRevealed` in the action's events and, for each id, calls `state.resolve_and_apply_information(&ids, Public, UntilZoneChange, Reveal)` and `state.remember_card_identities(all players, &ids)`. Both read `self.objects.get(id)` as it is at the boundary (`game_state.rs:26335-26356`, `:8122-8147` take `ObjectIncarnationRef::from_object` and the CURRENT zone).
- At the close, P1's seven revealed ids have already been returned to the shared pile, shuffled and partly redealt, so at the boundary each id is either in a library or in P0's or P1's NEW hand. Those cards get a public-reveal fact on their current incarnation. A revealed card that the shuffled pile deals back into either player's new hand therefore shows face-up to the opponent, and every revealed card in the pile is recorded as product knowledge for all players. By CR 400.7 the reveal was of the old hand object, so this is a hidden-information leak and a wrong game state, and it ships on the exact path the plan adds.
- The plan never read `remember_public_reveals`. Its only reveal-side claim ("`revealFanCards` handles ids that moved to a hidden library", UNESTABLISHED) concerns the animation, not this hook. No V-row would catch it (V3 asserts the event, not the information state).

Required revision (machinery is already in the engine; this is a plan decision to make explicit):
1. Section 3.4 item 2: emit the close's `CardsRevealed` with `card_ids: vec![]` and the 7 `card_names` (the field is `#[serde(default)]`, and `client/src/components/animation/revealFanCards.ts` already renders from names when ids and names differ in length), so the boundary hook publishes nothing; or name and justify another route that keeps the hook off the returned objects. Delete the sentence "no `revealed_cards` set is written because the hand leaves the zone in this same close" and replace it with the measured reason.
2. V3 gains a revert-failing assertion and a paired guard: after the close, for every id of P1's old hand, `state.information_active`-style public-reveal state is absent and `filter_state_for_viewer(state, P0)` shows none of the cards now in P1's new hand (and `filter_state_for_viewer(state, P1)` none of those in P0's new hand) with their identities; the pile objects are not in any viewer's remembered facts. Revert (emit the ids): the leak assertion goes red. Probe note: if the redeal never lands an old card in a hand for the seeded run, arrange the pile so it does (or assert on the pile objects' remembered facts instead).
3. Also check that the game-log entry (`game/log.rs:1338`) and the `derived_views.rs:3082` label render from names when ids are empty (the label uses `card_ids.len()`, which would read "revealed 0 cards"); if so, state the one-line adaptation inside `mulligan.rs`'s event construction or the log arm and add the file to the scope matrix as an engine-read-site addition.
