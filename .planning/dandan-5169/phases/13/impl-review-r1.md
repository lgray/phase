## Findings

**[HIGH]** `FreeReveal` is enumerated for every pending qualifying seat and every pending viewer receives the whole list, so a non-qualifying viewer is shown a FreeReveal button the engine refuses, and learns the opponent's hand qualifies (fewer than two lands or nonlands) before the reveal. Evidence: `candidate_actions_exact` in `crates/engine/src/ai_support/candidates.rs` (one candidate per pending entry, actor only in `metadata`); `legal_actions_for_viewer` in `crates/engine/src/ai_support/mod.rs` returns `legal_actions_full(state)` to any authorized pending viewer; `phase-server/src/main.rs` `build_game_started_message` and the StateUpdate fan-out send that full `Vec<GameAction>` to every `is_acting` seat (a `GameAction` carries no actor); `GamePage.tsx` `freeRevealOffered = legalActions.some(... "FreeReveal")` shows the button on existence alone. Probe (scratch, Dandan, P0 hand 0 lands/7 nonlands, P1 3/4): `offered(P0)=true offered(P1)=false`, `legal_actions_for_viewer(P1)` contains `MulliganDecision{FreeReveal}`, and `apply(P1, FreeReveal)` errs; control with neither qualifying: viewer P1 sees 0 FreeReveal candidates. Against the AI-vs-human wasm game the human is shown the button whenever the AI seat qualifies. Why it matters: the change's own "button only when the engine issued the action" and "no hand composition leaks" claims fail for the two-human and human-vs-AI case; Serum Powder never had this shape because the client derives per-object ids, while FreeReveal has no discriminator. Suggested fix: scope the emitted `MulliganDecision` candidates to the viewer's own entry at the engine seam every transport uses (filter by `metadata.actor == viewer` in the viewer-scoped legal-actions path and make the server/wasm payload sites use it), with a regression test that `legal_actions_for_viewer(P1)` lacks FreeReveal when only P0 qualifies and `legal_actions_for_viewer(P0)` has it.
